# commit

ステージされた内容を読み取り、必要ならブランチを作成し、リポジトリの慣習に沿った
メッセージでコミットする。**push はしない。PR も作らない。**

## 原則

**黙って実行する。** ブランチ名もコミットメッセージもユーザーに確認しない。
質問するのは「何をステージすべきか判断できない」場合だけ。

コミットは `--amend` で、ブランチ名は `git branch -m` で後から直せる。
確認のラウンドトリップを挟むより、妥当な判断で進めるほうが速い。

**慣習はリポジトリから読み取る。** ブランチ名の形式もコミットメッセージの形式も、
一般論やよくある規約を当てはめるのではなく、そのリポジトリの既存の履歴に合わせる。

## 手順

### 1. 状況を把握する

以下を **1 回のメッセージで並列に** 実行する。

```sh
git status --short
git diff --cached --stat
git diff --cached
git branch --show-current
git log --oneline -20
git branch -a
```

差分が巨大な場合は `git diff --cached --stat` と主要ファイルの `git diff --cached -- <path>`
に絞ってよい。**ただしメッセージを書くのに十分な内容は必ず読むこと。**
`--stat` だけを見て「〇〇を更新」のような中身のないメッセージを書かない。

### 2. ステージング内容を決める

**すでにステージされているものがあれば、それをそのまま使う。**
ユーザーが意図的にコミットを分割している可能性が高いので、勝手に `git add` で足さない。
（未ステージの変更が残っていても、それはこのコミットの対象外だと解釈する）

ステージが空の場合、未追跡・変更済みファイルを見て判断する。

**そのままステージしてよい場合**（質問せず `git add` する）:

- 変更が 1 つの論理的なまとまりになっている
- 直前に自分が編集したファイルだけが変わっている

**ユーザーに質問する場合**（AskUserQuestion を使う）:

- 無関係な変更が複数混ざっていて、1 コミットにまとめるのが不自然
- 用途のわからないファイルが含まれている（ビルド生成物か成果物か判断がつかない、
  デバッグ用の一時ファイルに見える、など）
- 秘匿情報が含まれていそうなファイル（`.env`、鍵、認証情報）がある

質問するときは「どれをコミットに含めるか」を選択肢で示す。
無関係な変更が混ざっているなら「分割して 2 回コミットする」も選択肢に入れる。

変更が何もない場合はその旨を伝えて終了する。空コミットは作らない。

#### 生成物とソースの区別

`.gitignore` にビルド生成物のパターンがあるリポジトリでは、生成物は `git status` に
現れないため `git add -A` で巻き込む危険は小さい。

一方で **git 管理外だがソースであるファイル** も存在しうる。これを `--force` で
追加してはいけないし、逆に生成物と誤認して削除してもいけない。
判断に迷うファイルは `git ls-files` で追跡状態を確認し、それでも不明ならユーザーに聞く。

リポジトリのルートに CLAUDE.md/AGENT.md などの規約ファイルがあれば、生成物の扱いについて
記述がないか確認する。

### 3. ブランチを決める

`git branch --show-current` の結果で分岐する。

**`main` / `master` / `develop` など共有ブランチにいる場合**
→ 新しいブランチを作成してチェックアウトする。

```sh
git switch -c <新しいブランチ名>
```

ブランチ名は **既存のブランチ名から慣習を読み取って** 決める。
`git branch -a` の出力（リモート追跡ブランチを含む）と、マージコミットの
`Merge pull request #N from <owner>/<branch>` に現れるブランチ名を見て、以下を揃える。

- プレフィックスの有無と語彙（`feat/` `fix/` `feature/` `bugfix/` など、実際に使われているもの）
- 区切り文字（`/` `-` `_`）
- 記述言語（英語か日本語か）
- 課題番号やユーザー名を含める慣習があるか

**既存の慣習が読み取れない場合**（履歴が浅い、ブランチが `main` だけ、など）に限り、
`<type>/<英語の kebab-case>` を使う。

同名のブランチが既にある場合は名前を変える（`-2` を付けるのではなく、より具体的な名前にする）。

**すでに作業ブランチにいる場合** → 何もしない。ブランチは切り替えない。
ステージ内容が現在のブランチのテーマと無関係に見えても、勝手に切り替えないこと。
それはユーザーの判断領域。

### 4. コミットする

メッセージのスタイルは `git log --oneline -20` から読み取って合わせる。
確認する点:

- Conventional Commits（`feat:` `fix:` など）を使っているか。使っている場合の type の語彙
- 記述言語（英語か日本語か）。混在している場合は多数派に合わせる
- 1 行目の長さの傾向、末尾に句点を付けるか
- 本文を書く慣習があるか、課題番号を含めるか

複数のスタイルが混在している場合は、**直近のコミットのスタイル**を優先する。

**「何を」ではなく「なぜ / 何が変わったか」を書く。**
`git diff --stat` を言い換えただけのメッセージ（「3 ファイルを修正」など）は書かない。

#### Co-Authored-By

**この会話セッション内で、自分が Edit / Write / NotebookEdit でファイルを編集したかどうか**
だけで判断する。ステージ内容との hunk 単位の照合はしない。

- 編集した → trailer を付ける
- 編集していない（ユーザーが自分で書いたコードをコミットするだけ）→ **付けない**

付ける場合の形式（本文との間に空行を 1 行挟む）:

```
Co-Authored-By: <<<your model name>>>
```

コミットの実行にはヒアドキュメントを使う。

```sh
git commit -F - <<'EOF'
feat: 〇〇を追加

必要なら本文。

Co-Authored-By: <<<your model name>>>
EOF
```

<<<your model name>>> はあなた自身の実行モデル名を記述する。

`-m` に改行を含む文字列を渡すとシェルのクォート処理でトラブルになりやすいので避ける。

### 5. 結果を報告する

`git log --oneline -1` と `git status --short` で結果を確認し、簡潔に報告する。

- 作成したブランチ名（作成した場合）
- コミットのハッシュとメッセージ 1 行目
- ステージせずに残した変更があればその旨

コミットに失敗した場合（pre-commit フックのエラーなど）は、
**失敗をそのまま報告する。** `--no-verify` で回避しない。

## やらないこと

- `git push`
- PR の作成
- `git commit --amend`（既存コミットの書き換えは明示的に依頼された場合のみ）
- `git reset` / `git checkout -- <file>` などの破壊的操作
- `--no-verify` でのフック回避
